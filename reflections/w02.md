# Proposal

| Backend | What it is | Role in my app | Why I picked it |
|---|---|---|---|
| **Class Ollama** | A hosted LLM endpoint at `llm.uvucs.org` provided through CS-3660, authenticated with my class API key | backend for everyday development and testing | It's free |
| **Claude API** | Anthropic's commercial LLM API (`api.anthropic.com`), authenticated with a personal API key | Higher-quality backend for final resume and cover letter output | Gives stronger responses than the Ollama models, so it is worth testing both |

| Setup piece | What I'll do | Why |
|---|---|---|
| **`.env` file** | Holds both API keys + a `LLM_BACKEND` variable | Keeps secrets out of source code never committed to git 🤫 |
| **Strategy interface** | Both backends expose the same method: `async complete(prompt) → string` | So the rest of my code doesn't care which backend is active |
| **Backend picker** | Reads `LLM_BACKEND` from `.env` and returns the right strategy | Makes switching a **config-only change** |

## Reflection

The Strategy pattern is a way to organize code so that different methods for doing the same task are kept in separate classes or files. In my project, the task is sending a prompt to an LLM and getting a response. Rather than mixing all the Claude and Ollama code together, I can give each backend its own strategy.

This method works well for my Job Pack project because I need multiple LLM backends. I chose Class Ollama as my main backend and Claude API as my backup. Class Ollama is free for everyday development, while Claude gives better responses for resumes and cover letters.

The clear benefit is that the rest of my app doesn't need to know which LLM is being used. My code can call the same method, like `complete`, no matter if the backend is Ollama or Claude. I can switch between them by changing `LLM_BACKEND` in my `.env` file instead of changing the code.

I’m very familiar with the strategy pattern and how it will benefit my project and future projects I plan to create. Doing the planning first before coding will save me time and energy that I won’t have to waste later when I have to do expansions, and prevent tight-coupling issues.
